#### Design Specificity Verdict

**LLM assessment**: The layout provides a clean "corporate canvas" (white) with teal accents, fitting the PropTech identity. However, the static `dir="rtl"` and `lang="ar"` on the root `<html>` tag completely undermines the multilingual nature of the site, causing severe structural mismatch when English is toggled via the client-side provider.
**Deterministic scan**: The CLI detector (`detect.mjs`) returned 0 findings (clean) for `src/app/layout.tsx`.
**Visual overlays**: Unavailable (no DOM mutation attempted as it's a structural critique).

#### Overall Impression
The overarching layout is clean, professional, and stays out of the user's way. However, the internationalization (i18n) implementation is fundamentally broken at the DOM root, which will severely degrade the experience for English speakers.

#### What's Working
1. **Font Strategy**: Loading Tajawal for Arabic and Space Grotesk/Inter for English provides excellent typography for both languages.
2. **Global Providers**: Cleanly orchestrated providers (PostHog, Analytics, Language) without cluttering the layout.

#### Priority Issues

- **[P0] Static HTML Language Attributes**
  - **Why it matters**: The `<html lang="ar" dir="rtl">` tags are hardcoded in the server layout. When a user switches to English, the document remains semantically Arabic and RTL unless the client-side provider hacks the DOM. Screen readers will also mispronounce everything.
  - **Fix**: Refactor to Next.js App Router i18n (e.g., `app/[lang]/layout.tsx`) OR ensure the `LanguageProvider` safely manages these attributes on the client.
  - **Suggested command**: `/impeccable harden`

- **[P1] Hardcoded `font-arabic` class on Body**
  - **Why it matters**: The `body` has `<body className="font-arabic">`. This forces Arabic typography settings globally, even when the user is reading English content.
  - **Fix**: Remove `font-arabic` from the static body and let the layout dynamically apply `font-ar` or `font-sans` classes based on the active language.
  - **Suggested command**: `/impeccable typeset`

#### Persona Red Flags

- **Sam (Accessibility-Dependent User)**: Screen readers will misinterpret English content because the document is statically declared as `lang="ar"`, causing screen readers to attempt an Arabic accent on English words. This is a critical WCAG failure.
- **Alex (Power User)**: Experiences layout thrashing or broken text direction when trying to browse the English version quickly.

#### Minor Observations
- The Skip to Content link in the Header uses `href="#hero-content"`, but ensure all pages actually have an element with `id="hero-content"`, otherwise it's a dead link on subpages.

#### Questions to Consider
- Should we migrate to proper Next.js locale routing (`/en/...` and `/ar/...`) to solve the structural i18n issues permanently?
- If we keep the client-side toggle, are we okay with the SEO hit of search engines only seeing the Arabic root?
